# 00. 개요

프롬프트 배틀 스펙 문서 세트의 시작점이다. 모든 항목 끝에 라벨을 붙였다.

- 라벨 뜻: 확정은 팀이 정한 것, 제안은 기본값으로 넣었지만 바꿀 수 있는 것, 미정은 아직 정하지 못해 08 문서에 모아 둔 것이다.
- 숫자 상수는 02 문서 6절에 표로 모았고, 코드에서는 `src/shared/constants.js` 하나만 참조한다.

## 1. 목표

- 두 유저가 같은 주제문을 받고, 주제어와 필수어를 직접 말하지 않은 채 AI가 그 내용을 설명하도록 프롬프트를 쓴다. [확정]
- AI 답변이 조건(필수어 포함, 분량)을 만족하면 PASS, 아니면 RETRY다. 제한시간 안에 PASS를 더 많이 쌓은 쪽이 이긴다. [확정]
- 프롬프트를 조리 있게 쓰는 연습을 게임으로 접근성 있게 만든다. [확정]
- 이번 작업의 직접 목표는 해커톤 마감까지 실제로 돌아가는 1대1 대전 데모다. [확정]

## 2. 대상

- 초등 고학년부터 대학생까지. [확정]
- 어린 사용자가 있으므로 채팅 기능은 넣지 않았고(이모지 포함), 닉네임은 금칙어를 거른다. [확정]
- 개인정보를 받지 않는 게스트 방식으로 시작한다. 만 14세 미만 개인정보 수집에 관한 법적 요건은 팀이 확인해야 한다. [미정]

## 3. 일정 제약

- 마감은 해커톤이며 2026-10-03 09:00이다. 시간대는 한국 시간으로 가정한다. [제안]
- 이 때문에 4주 일정은 폐기하고 마감 기준으로 마일스톤을 잡는다(07 문서). [확정]
- 제출 방식, 시연 형식(라이브인지 영상인지), 심사 기준은 아직 모른다. [미정]

## 4. 범위

| 단계 | 내용 | 라벨 |
|---|---|---|
| P0 데모 필수 | 코드 방 생성·입장, 방 설정(난이도, 시간, 프롬프트 제한), 대전 루프(각자 독립 진행), 전송 전 금지어 검사와 서버 재검사, Gemini 호출, 필수어·분량 판정, RETRY, 3연속 페널티 5초, 타이머와 종료, 결과 화면, 포기, 게스트 닉네임 | 확정 |
| P1 첫 공개 나머지 | 캐릭터 4종과 옷장, 건너뛰기, 한 번 더 하기, 재접속, 간이 튜토리얼, 임의 매칭 버튼(동작 없음), 동양풍 맵 연출 | 확정 |
| P2 이후 | 랭킹, 재화, 가챠, 참가비, 자유 채팅, 로그인, 동양풍 외 맵, 진짜 임의 매칭 | 확정 |

- 첫 공개 범위는 P0와 P1 전체이고, 해커톤 시간이 모자랄 때의 자르는 순서는 07 문서 5절에 있다. [확정]
- 동양풍 맵만 구현한다. 미래풍, 중세, 우주는 선택지에 안 나온다. [확정]
- 임의 매칭은 버튼만 둔다. 서버의 입장 로직은 코드 입장 하나로 통일해서 나중에 매칭이 같은 입구를 쓰게 한다. [확정]
- 기획서에 있는 "임의 매칭처럼 보이는 연출"은 하지 않는다. 확정 사항이 더 최신이라 그쪽을 따랐다. [제안]

## 5. 기술 스택

| 영역 | 선택 | 라벨 |
|---|---|---|
| 프론트 | HTML, CSS, JavaScript. 프레임워크 없음 | 확정 |
| 프론트 모듈 | ES 모듈(`<script type="module">`). 빌드 도구 없음 | 제안 |
| 서버 | Node.js와 웹소켓 | 확정 |
| 서버 라이브러리 | 실제 구현은 Express와 Socket.IO(웹소켓 우선)로 정적 파일과 실시간 통신을 한 프로세스에서 서빙한다. 처음 제안한 `ws`보다 재접속과 방 처리가 편해서 구현을 따른다 | 제안 |
| AI | Gemini Flash 계열. 유저 프롬프트를 그대로 전달하고 시스템 프롬프트는 없음 | 확정 |
| 판정 | AI 없이 `promptRules.js`로만 | 확정 |
| 저장소 | 첫 공개는 서버 메모리. 서버를 다시 켜면 방이 사라지는 것을 허용 | 제안 |
| 배포 | 단일 서버 프로세스. 시연 환경(로컬 터널인지 공개 호스팅인지)은 모름 | 미정 |
| 화면 크기 | 데스크톱 1024x600 이상 우선, 모바일은 이후 | 제안 |
| 소리와 배경음 | 첫 공개에서 제외 | 제안 |

## 6. 팀과 역할

- 4명이고 역할은 서버 전문, UI 전문, 모델 전문, 올라운더다. 전문 밖의 일도 할 수 있다. [확정]
- 작업 분담과 인터페이스는 07 문서에 있다.
- UI는 현재 개발 중이며, 완성되면 저장소에 올린다. 그래서 UI는 서버 없이 목(mock) 전송 계층으로 먼저 개발하고, 04 문서의 이벤트 명세를 정본으로 삼는다. [확정]

## 7. 핵심 설계 원칙

1. 서버가 기준이다. 타이머, 점수, 문제 배포, 페널티는 서버가 정하고 클라이언트는 표시만 한다. [확정]
2. 금지어 검사는 UI와 서버가 같은 규칙 파일을 써서 양쪽에서 한다. 서버 검사가 최종이다. [확정]
3. 판정은 코드가 한다. AI 평가 연출은 유저가 결과를 읽고 배우게 하는 UI 연출일 뿐이다. 판정은 항상 연출보다 먼저 서버에서 확정되고, 연출은 확정된 판정을 따라간다. [확정]
4. 두 사람이 같은 순서의 문제 목록을 받고, 각자 자기 속도로 풀며 PASS하면 자기 다음 문제로 넘어간다. [확정]
5. 두 사람의 판은 같은 시각에 끝난다. AI 대기 시간은 타이머에서 빼지 않는다. [확정]
6. 상대의 프롬프트는 숨기고 AI 답변은 보여준다. [확정]

## 9. 용어집

| 용어 | 뜻 |
|---|---|
| 주제문 / 문제 | 한 번에 풀 단위. 주제어, 필수어 3개, 난이도, 추가금지어로 이루어진 `problem`과 분량 `lengthRule`의 조합 |
| 주제어 | 문제의 주제. 프롬프트에 쓰면 안 된다 |
| 필수어 | AI 답변에 들어가야 하는 단어. 문제마다 3개. 프롬프트에는 쓰면 안 된다 |
| 추가금지어 | 영어 번역어 같은, 필수어 외에 막는 단어 |
| 금지어 | 주제어, 필수어, 추가금지어를 합친 것 |
| 난이도 | 쉬움은 필수어 1개 이상, 보통은 2개 이상, 어려움은 3개 모두 필요 |
| 분량 | AI 답변의 길이 조건. 8가지 중 문제와 독립으로 뽑는다(`lengthRule`) |
| 프롬프트 제한 | 유저 프롬프트의 최대 글자 수. 방 설정값이며 50, 100, 150, 300, 무제한(null) |
| 시도(attempt) | 한 문제에서 프롬프트를 한 번 전송한 것. 금지어로 막혀 전송되지 않은 것은 시도가 아니다 |
| PASS / RETRY | AI 답변이 조건을 만족하면 PASS, 아니면 RETRY |
| 한 번에 PASS | 그 문제에서 첫 번째 시도로 PASS한 것 |
| 연속 PASS(streak) | 한 번에 PASS를 이어 간 횟수. 3이 되면 페널티 |
| 페널티 | 상대의 입력을 5초 잠그는 것 |
| 건너뛰기 | 점수 없이 다음 문제로 가는 것. 규칙은 다시 정해야 한다(02 문서 3.3) |
| 연출 | 답변 재생, 평가 읽기, PASS/RETRY 화면. 판정이 아니라 표시다 |
| 전환(intermission) | 한 문제가 끝나고 다음 문제가 열리기까지의 시간 |
| 방 코드 | 방에 들어가기 위한 6자리 코드 |
| 호스트 / 게스트 | 방을 만든 사람 / 코드로 들어온 사람 |
| 점수 | 한 판에서 PASS한 문제 수. 기획서의 "포인트(맞춘 주제 수)"를 이 말로 통일한다 |
| 코인 / 랭크 점수 | 이후 단계의 재화와 랭크. 점수와는 다른 값 |
| 서버 시각 | 서버의 에포크 밀리초. 모든 시간 표시는 이 값을 기준으로 한다 |
| 유예(grace) | 종료 순간에 처리 중인 요청을 기다려 주는 시간 |
| 스냅샷 | 재접속한 클라이언트에게 보내는 현재 방과 게임 전체 상태 |
